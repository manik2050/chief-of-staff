# API testing techniques, part 2

Learning evidence for Day 28 system design. Not part of the Chief of Staff
install. The installer does not copy this folder.

Part 1 ([API testing](../api-testing/)) covers types 1-25. This letter
names 28 more (26-53); its public teaser defines seven, sketched here.
Circuit breaker through component testing (33-53) are named, not defined.
Fuzz testing sends randomized, malformed, unexpected data, generated by an
algorithm, mutated from valid inputs, or pulled from attack-pattern
libraries, to find crashes, memory leaks, unhandled exceptions, and
security holes (AFL, Burp Suite, Restler). Penetration testing is a
skilled professional or team simulating a real attack: chaining bugs,
business-logic flaws, and social-engineering vectors tools miss. The goal
is not a checklist but whether a motivated attacker can break in.
Injection attack testing crafts SQL, NoSQL, command, LDAP, and header
payloads that try to escape the input context and run as code; one
success is a critical vulnerability. Encryption/TLS testing checks that
the API enforces HTTPS, rejects HTTP, uses strong TLS versions and
ciphers, and presents a valid, unexpired, correctly chained certificate
(testssl.sh, sslyze, nmap). Policy/compliance testing checks GDPR, HIPAA,
PCI-DSS, and SOC 2 controls: personal data encrypted, audit logs written,
retention enforced, consent working. Reliability testing asks whether the
API gives the right answer across thousands of requests, network
disruptions, and partial failures (uptime, error rate, MTBF). Chaos
testing kills instances, injects latency, corrupts DNS, and fills disks
while watching whether the API keeps serving or degrades predictably;
Netflix's Chaos Monkey randomly terminates production instances during
business hours.

```
  input                         over time / failure
  -----                         -------------------
  fuzz: random / mutated /      reliability: many calls,
        attack-library          not one run (uptime, error
  injection: payload stays      rate, MTBF)
        data, never code        chaos: kill one instance or
  pen test: human attacker,           +200ms; staging first
        snapshot, not continuous
  TLS: HTTPS, 1.2+, valid chain
  compliance: GDPR / HIPAA / PCI-DSS / SOC 2
```

```python
# Toy in-process checks, not AFL or a pen test. python3 - <<'PY' ... PY
def naive_sql(name):
    return "SELECT id FROM items WHERE name='" + str(name) + "'"

def handle(body):
    name = body.get("name") if isinstance(body, dict) else None
    if not isinstance(name, str):
        raise TypeError("unhandled")
    if "'" in name or not (1 <= len(name) <= 8):
        return 400, "bad name"
    return 200, ("SELECT id FROM items WHERE name=?", (name,))

payload = "x'; DROP TABLE items;--"
print("inject naive", "DROP" in naive_sql(payload))
print("inject handle", handle({"name": payload}))

mutants = [None, {"name": None}, {"name": "mug" * 9},
           {"name": "mug';--"}, [], {"name": 1}]
crashes = rejects = 0
for m in mutants:
    try:
        status, _ = handle(m)
        rejects += status == 400
    except Exception:
        crashes += 1
print("fuzz", "crashes", crashes, "rejects", rejects)
# inject naive True
# inject handle (400, 'bad name')
# fuzz crashes 4 rejects 2
```

Fuzz finds bugs no human would look for, but results are noisy; run it
continuously on input-parsing endpoints and treat every crash as a
potential security issue. Pen tests are the most realistic check, but
expensive, only as good as the tester, and a snapshot; schedule them
before major launches and at least annually. Injection can expose a whole
database or a shell, and every field, header, query parameter, and path
segment is in scope; use parameterized queries and sanitization, then
verify they hold. TLS checks are easy to forget and degrade as certs
expire and protocols age; one HTTP endpoint can leak credentials or
session tokens, so enforce TLS 1.2+, monitor expiry, and scan every
deploy. Compliance is non-negotiable for sensitive data but rigid (GDPR
fines up to 4% of global annual revenue); map each requirement to a test
and run it every release. Reliability numbers drive SLAs and SLOs but
take weeks of monitoring. Chaos finds gaps nothing else will, and a badly
scoped run can cause a real outage: start in staging with a small blast
radius, kill one instance or add 200ms latency to one dependency.
