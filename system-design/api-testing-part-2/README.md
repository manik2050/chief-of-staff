# API testing techniques, part 2

Learning evidence for Day 28 system design. Not part of the Chief of Staff
install. The installer does not copy this folder.

Part 1 ([API testing](../api-testing/)) already covers the academy's first
public seven (smoke through acceptance). This letter is the second half of
that series: it names 28 further types, numbered 26-53. The free teaser
defines seven of them (fuzz through chaos). Circuit-breaker testing through
component testing are listed in the contents, not defined here.

Fuzz testing sends randomized, malformed, unexpected data — generated by an
algorithm, mutated from a valid payload, or taken from an attack-pattern
library, not designed by a human — to find crashes, memory leaks, unhandled
exceptions, and security holes. Named tools: AFL, Burp Suite, Restler.
Penetration testing is a skilled human (or team) simulating a real attack:
chaining bugs, business-logic flaws, and social-engineering paths that tools
miss. The goal is whether a motivated attacker can break in, not a checklist.
Injection attack testing crafts SQL, NoSQL, command, LDAP, and header
payloads so input stays data and never executes as code. One success is a
critical vulnerability; every field, header, query parameter, and path
segment is in scope. Encryption/TLS testing checks that the API enforces
HTTPS, rejects HTTP, uses strong TLS versions and ciphers, and presents a
valid, unexpired, correctly chained certificate. Named tools: testssl.sh,
sslyze, nmap. Policy/compliance testing checks GDPR, HIPAA, PCI-DSS, and
SOC 2 controls: personal data encrypted, audit logs written, retention
enforced, consent working. Reliability testing is not one response. It asks
whether the API still returns the right answer across thousands of calls,
network disruption, and partial failure, via uptime, error rate, and mean
time between failures. Chaos testing injects real failures — kill an
instance, add latency, corrupt DNS, fill a disk — and watches whether the
API keeps serving or degrades on purpose. Netflix's Chaos Monkey is named:
it terminates production instances during business hours.

The teaser names, but does not define: circuit breaker, backpressure, fault
injection, failover, recovery, idempotency, timeout and retry, caching, data
integrity, data consistency, state transition, UI-level API, developer
experience, documentation, rate limiting, backward compatibility, mutation,
mock/stub, synthetic monitoring, scenario/workflow, and component testing.

```python
# Toy in-process checks, not AFL or a pen test. python3 - <<'PY' ... PY
def naive_sql(name):
    return "SELECT id FROM items WHERE name='" + str(name) + "'"

def handle(body):
    name = body.get("name") if isinstance(body, dict) else None
    if not isinstance(name, str):
        raise TypeError("unhandled")
    if "'" in name or not (1 <= len(name) <= 8):
        return 400, "bad name"
    return 200, naive_sql(name)

payload = "x'; DROP TABLE items;--"
print("inject naive", "DROP" in naive_sql(payload))
print("inject handle", handle({"name": payload}))

mutants = [None, {"name": None}, {"name": "mug" * 9},
           {"name": "mug';--"}, [], {"name": 1}]
crashes = rejects = 0
for m in mutants:
    try:
        status, _ = handle(m)
        rejects += status == 400
    except Exception:
        crashes += 1
print("fuzz", "crashes", crashes, "rejects", rejects)
# inject naive True
# inject handle (400, 'bad name')
# fuzz crashes 4 rejects 2
```

Fuzz finds cases no person would write, but results are noisy (duplicates,
low-severity); the letter says run it continuously on input-parsing
endpoints and treat every crash as a possible security issue. Pen tests are
the most realistic security check and a point in time: before a major
launch, and at least annually; they cost, they take time, and they are only
as good as the tester. Injection testing is wide — every input vector — and
catches a class of bugs that can expose a database or a shell; use
parameterized queries and sanitization, then verify those defenses hold.
TLS checks are easy to skip and rot as certificates expire and protocols
age; the letter says enforce TLS 1.2+ on every endpoint, watch expiry, and
scan on every deploy (one HTTP endpoint can leak credentials or session
tokens). Compliance is non-negotiable for sensitive data and rigid;
requirements change slowly and tests must follow. Map each rule to a test
and rerun every release (the letter cites GDPR fines up to 4% of global
annual revenue, and HIPAA reporting plus possible criminal charges).
Reliability numbers feed SLAs and SLOs but need weeks of watching, not
minutes. Chaos finds gaps nothing else will, and a badly scoped run can
cause a real outage: start in staging, small blast radius, kill one instance
or add 200ms of latency to one dependency.
